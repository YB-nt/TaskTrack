# Swift Integration QA

가장 흔하고 정적 분석으로 놓치기 쉬운 결함은 두 컴포넌트가 각각 "올바르게" 구현되어 있지만 경계면에서 계약이 어긋나는 경우다. Swift의 타입 시스템도 `Any`, 강제 캐스팅, 옵셔널 체이닝 뒤에 숨은 불일치는 컴파일 시점에 잡지 못한다. 이 스킬은 경계면을 명시적으로 교차 비교하는 절차를 정의한다.

## 검증 절차

### 1. 빌드 검증 (최우선 게이트)

```bash
xcodebuild -list                                              # 스킴 확인
xcodebuild -scheme <SchemeName> -destination 'platform=macOS' build

# Swift Package(Taskflow)인 경우
swift build
```

빌드가 실패하면 다른 검증보다 먼저 이 문제를 리포트한다 — 빌드가 안 되면 이후 검증이 무의미하다.

**자동 검증 실행:** 이 프로젝트는 CLT뿐인 환경(`swift test` 불가 — `swiftui-app-development` 스킬 참조)이라 `swift run TaskflowVerify`로 회귀 검증을 돌린다. 새 파싱/스케줄 로직을 추가했으면 `Sources/TaskflowVerify/main.swift`에 해당 assertion을 추가하고 통과를 확인한다.

**시각 검증의 한계:** 이 세션에는 Screen Recording/Accessibility 권한이 없어 `screencapture`나 System Events UI 스크립팅으로 실행 중인 앱을 확인할 수 없다(2026-07-30 확인됨). `swift run Taskflow`로 앱을 띄운 뒤 프로세스가 살아있는지·크래시 리포트가 없는지까지만 자동 확인하고, 실제 화면 톤/레이아웃이 디자인과 맞는지는 사용자에게 직접 봐달라고 요청한다.

### 2. View ↔ ViewModel 경계면 검증

**반드시 두 파일을 동시에 연다.** ViewModel만 보거나 View만 봐서는 불일치가 보이지 않는다.

```
검증 단계:
1. ViewModel의 @Published/@Observable 프로퍼티 목록과 타입을 추출한다.
2. 대응 View에서 실제로 참조하는 프로퍼티 이름과, 그 값을 사용하는 방식(옵셔널 언래핑 여부 등)을 확인한다.
3. 이름/타입이 정확히 일치하는지 비교한다. (예: ViewModel에 `upcomingEvents: [Event]`가 있는데 View가 `events`를 참조 — 컴파일 에러로 잡히지만, 제네릭/Any 사용 시 컴파일 통과하고 런타임에만 드러날 수 있다)
4. ViewModel의 메서드(예: `markAsHandled(_:)`)가 View의 버튼/제스처 핸들러에서 실제로 호출되는지 확인한다 — 메서드가 정의만 되고 어디서도 호출되지 않으면 "죽은 기능"이다.
```

### 3. 디자인 스펙 ↔ 구현 화면 충실도 검증

```
검증 단계:
1. `_workspace/01_design_spec/screens/{screen}.md`에서 레이아웃, 컴포넌트 배치, 상태별 스펙을 읽는다.
2. 대응 SwiftUI View 코드를 읽고 실제 레이아웃 구조를 확인한다.
3. 스펙에 정의된 모든 상태(빈 상태/로딩/에러 등)가 View 코드에 실제로 분기 처리되어 있는지 확인한다 — 기본 상태만 구현하고 나머지 상태가 누락되는 경우가 흔하다.
4. 색상/폰트/spacing이 `DesignTokens`를 참조하는지, 하드코딩된 값이 섞여 있지 않은지 확인한다.
5. 스펙에 `(추정)`으로 표기된 값은 구현이 스펙과 다르더라도 낮은 우선순위 FIX로 분류한다 — 추정치 자체가 불확실하기 때문이다.
```

### 4. 모니터링 트리거 ↔ 알림 실행 검증

```
검증 단계:
1. 정의된 모니터링 조건(예: "일정 10분 전 알림")을 코드에서 찾는다.
2. 해당 조건이 실제로 UNUserNotificationCenter 호출로 이어지는지 추적한다.
3. 조건은 정의되어 있지만 알림 호출로 연결되지 않은 "죽은 트리거"가 없는지 확인한다.
4. Info.plist에 필요한 알림 권한 설명이 있는지, requestAuthorization이 앱 시작 시 호출되는지 확인한다.
```

## 판정 및 리포트

각 항목을 PASS / FIX / REDO로 판정하고 `_workspace/03_qa_report_{n}.md`에 기록한다. FIX/REDO는 반드시 파일:라인과 구체적 수정 방향을 포함한다 — "여기 문제 있음" 수준의 모호한 지적은 재작업 루프만 늘린다.

## 원칙

- **존재 확인이 아니라 교차 비교를 한다.** "ViewModel에 프로퍼티가 있는가"가 아니라 "View가 참조하는 이름/타입과 정확히 일치하는가"를 확인한다.
- **각 모듈(화면/기능) 완성 직후 검증한다.** 전체 완성 후 한 번에 몰아서 하면 초기 경계면 불일치가 후속 구현 전체에 전파된 뒤에야 발견된다.
- **빌드 통과는 정합성을 보장하지 않는다.** 타입 캐스팅이나 옵셔널 강제 언래핑이 있으면 빌드는 성공해도 런타임에 실패할 수 있다 — 이런 지점을 우선적으로 의심한다.
